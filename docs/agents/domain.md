# Domain documentation

This project has one context. Read the root `GLOSSARY.md` before naming domain concepts. Use its terms consistently and update it when a term is agreed.

Read relevant decision beads and the current spec before designing or changing behavior. Record decisions and specs in beads, as described in `issue-tracker.md`. Where a decision conflicts with an existing record, surface the conflict and obtain a new decision rather than silently replacing it.

Keep development documentation and research in the main repository. User documentation belongs in the separately versioned wiki submodule once its remote is initialized. The provisioning status is tracked in beads.

Create additional documents only when they contain information that has been established. Link to decision records rather than copying their detail into ADR files.
